# TypeScript runtime lifecycle

`runPreparedRun` owns the Paper process, control listener, Mineflayer clients, run lease, trace, and cleanup. It uses a fresh run directory and clones the immutable prepared world template into `server/world` before starting the match server. Competitors are headless bots; scenario spectator capacity is filled by separate spectator clients. Paper binds game traffic to `127.0.0.1:25565`.

The runtime authenticates the plugin over a loopback control socket, validates its ready identity against the repository plugin descriptor, sends the compiled prepare command, waits for all clients, and then starts the match or passes control to an evaluator. The plugin owns player modes. After a terminal event, the runtime stops issuing policy decisions, joins active skills, stops and reaps Paper, finalizes the v2 trace, reads stopped player stats, and releases the run lease.

`RunPreparedRunOptions` requires `acceptMinecraftEula: true`; the runtime rejects missing acceptance before reading run inputs. The CLI likewise requires `--accept-minecraft-eula` before artifact lookup or preparation. Optional `onRosterReady` runs after the authenticated server and complete automated roster are ready, before match start or evaluation. It reports the loopback host, game port, and server Minecraft/protocol versions; callback failure fails the run. The CLI uses it to print spectator connection details to stderr while keeping final JSON on stdout.

Optional `spectatorMode` defaults to `automated`. `reserveExternalSlot` starts one fewer automated spectator within the scenario's existing capacity, leaving one game connection for an external native spectator; zero capacity is rejected. The CLI exposes this as `--reserve-external-spectator-slot`, validates it before run preparation, and `make server` selects it. Server capacity and competitive identities are unchanged. Acceptance runs retain all configured automated spectators.

`make server` also waits for one connected player outside the runtime-owned bot and spectator roster before it sends the match start command. It does not need the external player's username. Until that player joins, the plugin remains in `WAITING` and holds competitors at their assigned map spawns. Native and automated spectators are placed at the rounded center of the configured bot spawns, so the external spectator joins beside the group. The usual Hunger Games runtime deadline still applies while waiting.

The CLI applies a 180 second cold-start deadline, a 60 second per-server readiness deadline, and a wall deadline of 600 seconds for Hunger Games or 1,200 seconds for Civilization. The runtime derives that limit from the validated scenario mode and arms it before server preparation; it remains active through match execution and cleanup. Deadlines fail with a structured runtime timeout. Cleanup preserves the initiating error and reports cleanup failure separately. An interrupted run retains its structured failure artifact and any completed trace checkpoints; cancellation does not invent a terminal outcome. A genuine operator-abort outcome may be emitted during cleanup after cancellation when backed by its preceding recorded runner operator-abort command and independently validated authority events; it cannot be replaced by a winner, draw, or fabricated outcome.

The resource monitor aborts when combined owned RSS exceeds 8 GiB, process-available memory falls below 4 GiB, or swap-outs increase. Swap-in-only activity is permitted; both system-wide counters remain in opt-in samples. These counters do not identify which process caused the activity. Live admission reserves 8 GiB available memory and checks stable swap-outs before launch.

- `./arena test --suite integration --case lifecycle-smoke` runs one real short match, checks Paper reaping and both game/control socket release, then uses the GC CLI to archive the exact trace and stopped stats before removing the live run directory.
- `./arena test --suite integration --case lifecycle` repeats that lifecycle ten times sequentially and archives every two completed runs. This keeps the number of live run directories below the native helper's ten-run limit while preserving their evidence in the archive.
- `./arena test --suite integration --case faults` runs five fault selectors sequentially: occupied game port, competing run-lease owner, mismatched loaded plugin, externally killed Paper process, and SIGINT cancellation through the CLI process. Crash evidence must have no plugin outcome; cancellation may preserve a genuine recorded operator-abort outcome and independently valid authority events.

The shutdown stop-write race now has real-child coverage: an externally signal-killed child may report `EPIPE` before Node delivers exit, and cleanup accepts that error only after the stop attempt, a reaped signal exit, and no owner-requested termination. A live child that closed stdin still fails with `console_write_failed`. The Paper crash/SIGINT selectors have not been rerun on this correction. The owner authorized a one-time archival exception for two never-started preparations; their complete original directories are retained under the archive namespace, restoring two run slots. Other protected failures and shipped GC rules are unchanged.

## Policy decisions and owned actions

Every configured strategy tick reobserves eligible competitors, including those navigating or attacking. New traces record `policy-replay-v2` decisions with a disposition: `hold`, `start`, `continue`, `defer`, or `replace`. An action's identity is its initiating decision sequence. Continued and deferred decisions reference that existing action and produce no extra effect. Replacement decisions identify the previous action and explain `higherPriority` or `targetChanged`; they are accepted before cleanup finishes. A reserved action waiting for cleanup is reported as `defer` with `cleanupPending`, and never as a running continuation. The strict replay reader retains explicit support for recorded v1 decisions.

Priority is border escape, retreat, hunger recovery, equipment improvement, visible combat, loot, remembered-opponent search, and exploration. A fresh exploration proposal defers with `goalPersistence` while the existing exploration route remains owned, until that bounded skill settles. Other equal priority target changes wait two strategy intervals; higher priority decisions bypass that hysteresis on the next configured tick. Identical intents preserve the current skill. Each seat has one control owner and at most one reserved successor. A successor starts after the previous owner's cancellation and effect settlement; cleanup is bounded at five seconds, and a cleanup failure quarantines the seat and fails the run. Superseded reservations record cancellation without claiming they executed. Shutdown stops decisions, cancels owned actions, joins their tasks, removes observation listeners, and leaves the outcome segment private until Paper stops.

Registered path searches detach returned `Move` nodes and action arrays from AStar's frontier before the pinned pathfinder formats or consumes them. This applies to admitted computation and worker-denied partial results. It prevents block-center formatting from invalidating an integer exact goal while preserving the existing search budgets, goal checks, and deadlines.

Checkpoints at 200, 400, and subsequent decision counts are ordered beside the recorded decisions. The checkpoint watermark counts recorded observations and decisions, rather than completed effects. A skill still running at a checkpoint has no completed effect in that segment. Its real outcome may appear in a later segment, including after the authoritative outcome during shutdown.

Internal acceptance evaluators may provide `onPolicyActivity` and `onResourceSample` callbacks. Decision timing measures from the runtime's receipt of a public clock through acceptance, separately from action execution and cleanup settlement. Action samples identify the initiating decision, report a null start time for reservations that never execute, and describe thrown failures separately from skill outcomes. Callbacks receive diagnostic events and cannot add policy observations. Callback errors fail the run.


## Civilization adapter

Civilization preparation uses the scenario's fixed border, canonical six-seat faction roles, starting kit, capture zone, and outpost anchors. Each competitor owns one Civilization client adapter and receives its public roster and faction objective. Policies consume that client's received inventory, blocks, entities, and permitted team reports. The shared policy loop forwards completed shared-action and material-action feedback to Civilization decisions and preserves action cancellation barriers, death quarantine, and checkpoint settlement behavior.

Resource reports originate from the sender's current local resource observation. The runtime binds sender identity to its owned competitor handle, encodes one bounded local frame, and delivers only to other seats in the same faction. It admits at most one report per sender per 20 match ticks and measures the encoded frame against the 1 KiB limit before decoding. The client observer enforces its 16-message queue and 200-tick age limit at the current match tick. These local frames do not establish a network transport proof. Civilization skills retain failed and partial progress outcomes in mode-specific effect records and feed material-action receipts back to the next decision with their actual start and completion ticks. Civilization memory stores bounded failed material targets beside its nested shared policy memory. Cancellation releases ownership without becoming failed-target evidence.

The Civilization runtime adapter's preparation, policy lifecycle, action feedback, and faction relay have focused source coverage. Real Paper acceptance remains gated on the campaign's Hunger Games milestone and independent integration verification.
