# TypeScript runtime lifecycle

`runPreparedRun` owns the Paper process, control listener, Mineflayer clients, run lease, trace, and cleanup. It uses a fresh run directory and clones the immutable prepared world template into `server/world` before starting the match server. Competitors are headless bots; scenario spectator capacity is filled by separate spectator clients. Paper binds game traffic to `127.0.0.1:25565`.

The runtime authenticates the plugin over a loopback control socket, validates its ready identity against the repository plugin descriptor, sends the compiled prepare command, waits for all clients, and then starts the match or passes control to an evaluator. The plugin owns player modes. After a terminal event, the runtime stops issuing policy decisions, joins active skills, stops and reaps Paper, finalizes the v2 trace, reads stopped player stats, and releases the run lease.

`RunPreparedRunOptions` requires `acceptMinecraftEula: true`; the runtime rejects missing acceptance before reading run inputs. The CLI likewise requires `--accept-minecraft-eula` before artifact lookup or preparation. Optional `onRosterReady` runs after the authenticated server and complete automated roster are ready, before match start or evaluation. It reports the loopback host, game port, and server Minecraft/protocol versions; callback failure fails the run. The CLI uses it to print spectator connection details to stderr while keeping final JSON on stdout.

Optional `spectatorMode` defaults to `automated`. `reserveExternalSlot` starts one fewer automated spectator within the scenario's existing capacity, leaving one game connection for an external native spectator; zero capacity is rejected. The CLI exposes this as `--reserve-external-spectator-slot`, validates it before run preparation, and `make server` selects it. Server capacity and competitive identities are unchanged. Acceptance runs retain all configured automated spectators.

The CLI applies a 180 second cold-start deadline, a 60 second per-server readiness deadline, and a 600 second wall deadline. Deadlines fail with a structured runtime timeout. Cleanup preserves the initiating error and reports cleanup failure separately. An interrupted run retains its structured failure artifact and any completed trace checkpoints; cancellation does not invent a terminal outcome. A genuine operator-abort outcome may be emitted during cleanup after cancellation when backed by its preceding recorded runner operator-abort command and independently validated authority events; it cannot be replaced by a winner, draw, or fabricated outcome.

## Policy decisions and owned actions

Every configured strategy tick reobserves eligible competitors, including those navigating or attacking. New traces record `policy-replay-v2` decisions with a disposition: `hold`, `start`, `continue`, `defer`, or `replace`. An action's identity is its initiating decision sequence. Continued and deferred decisions reference that existing action and produce no extra effect. Replacement decisions identify the previous action and explain `higherPriority` or `targetChanged`; they are accepted before cleanup finishes. A reserved action waiting for cleanup is reported as `defer` with `cleanupPending`, and never as a running continuation. The strict replay reader retains explicit support for recorded v1 decisions.

Priority is border escape, retreat, hunger recovery, equipment improvement, visible combat, loot, remembered-opponent search, and exploration. A fresh exploration proposal defers with `goalPersistence` while the existing exploration route remains owned, until that bounded skill settles. Other equal priority target changes wait two strategy intervals; higher priority decisions bypass that hysteresis on the next configured tick. Identical intents preserve the current skill. Each seat has one control owner and at most one reserved successor. A successor starts after the previous owner's cancellation and effect settlement; cleanup is bounded at five seconds, and a cleanup failure quarantines the seat and fails the run. Superseded reservations record cancellation without claiming they executed. Shutdown stops decisions, cancels owned actions, joins their tasks, removes observation listeners, and leaves the outcome segment private until Paper stops.

Checkpoints at 200, 400, and subsequent decision counts are ordered beside the recorded decisions. The checkpoint watermark counts recorded observations and decisions, rather than completed effects. A skill still running at a checkpoint has no completed effect in that segment. Its real outcome may appear in a later segment, including after the authoritative outcome during shutdown.

Internal acceptance evaluators may provide `onPolicyActivity` and `onResourceSample` callbacks. Decision timing measures from the runtime's receipt of a public clock through acceptance, separately from action execution and cleanup settlement. Action samples identify the initiating decision, report a null start time for reservations that never execute, and describe thrown failures separately from skill outcomes. Callbacks receive diagnostic events and cannot add policy observations. Callback errors fail the run.
