# Determinism and evidence

## TypeScript trace-v2 and trace-v3 reading

The TypeScript runner accepts historical trace schema version 2 and current version 3. The strict envelopes are defined by the [trace-v2 schema](../schemas/trace-v2.schema.json) and [trace-v3 schema](../schemas/trace-v3.schema.json). Both require exactly the listed envelope fields and a trailer equal to `{ "complete": true }`. Trace-v3 carries `policy-replay-v3` records, whose input and replay contract is described in [policies](policies.md#determinism-and-outcomes); trace-v2 rejects that policy record version. Generic inspection preserves record objects as written; `report` and `replay-policy` interpret only their documented typed records. Duplicate JSON object names are rejected recursively before a JavaScript object can overwrite one.

A segment's `records` array is the sequential stream. JSON nesting is limited to 32 containers per segment. `first_sequence` and `last_sequence` are canonical unsigned decimal strings from 1 through 18446744073709551615. The number of records must equal `last_sequence - first_sequence + 1`, calculated without integer overflow; array index therefore determines each record's sequence. Across supplied segments, the runner orders by `first_sequence`, requires one `run_id`, and rejects gaps, overlaps, and sequence overflow. This reconstructs a complete ordered span from the supplied files; it cannot establish that the span covers the full run.

The `sha256` field is the lowercase SHA-256 digest of the compact serialization of the `records` array only. The byte sequence is UTF-8 with no whitespace: object keys use JavaScript's default string sort order, arrays keep their order, and numbers use `JSON.stringify` serialization. Non-finite values and integer-valued numbers outside JavaScript's safe integer range are rejected. The digest excludes the envelope, `run_id`, trailer, and checksum text. Producers must use the same canonicalization. Trace-v1 files use numeric sequence fields and a different canonicalization; the TypeScript reader rejects them instead of interpreting them as schema 2 or 3.

## Java world-plan transfer

The TypeScript encoder writes schema 1 for planned maps and schema 2 for natural terrain maps. Schema 1 has `schema`, `run_id`, `map_semantic_id`, `dimensions`, `blocks`, `spawns`, and `loot_containers`. Schema 2 has `schema`, `run_id`, `world_seed`, `map_semantic_id`, `terrain`, `dimensions`, `blocks`, `spawns`, and `loot_containers`. Schema 2 uses a canonical unsigned decimal string for `world_seed`, `terrain: "vanilla"`, dimensions `{ "width": 1024, "depth": 1024 }`, an empty `blocks` array, and `column: { "x", "z" }` for each spawn and loot container. Both versions preserve canonical array order, contiguous spawn seats from zero, and inventory order. The compact UTF-8 plan is capped at 128 MiB. `tests/fixtures/world-plan/world-plan-v1.json` and `tests/fixtures/world-plan/world-plan-v2.json` are shared with the Java reader. `prepare` writes the plan to `.work/arena/runs/<run-id>/world-plan.json` using the native handle-relative filesystem helper. It creates the run directory exclusively and publishes the plan without overwriting an existing file.

Java `MapPlanReader` reads schema 1 and 2 strictly. It rejects duplicate JSON names and unknown fields. It verifies the map semantic ID. For schema 2, the runner sets `server.properties` `level-seed` to the signed 64-bit Java representation of `world_seed`. It omits the Bukkit custom generator setting. Paper then uses its vanilla generator. The plugin centers the world border on the arithmetic mean of the configured spawn columns. It prepares only chunks around spawn and cache columns with their configured view-distance halos. It resolves each column against the generated world. Every spawn needs nonhazardous solid support and two clear blocks. Spawn seats need at least two horizontal blocks of separation. Each cache chest needs support, headroom, and an adjacent interaction position. The plugin places or fills chests only after all checks pass. It sends readiness after setup succeeds.

## Core policy replay input

`@arena/core` normalizes `policy-input-v2` with one validated observation, its policy memory, an ordered feedback batch of at most two completed skill outcomes, parameters, and the pre-decision RNG state. Historical `policy-input-v1` keeps its original memory shape and is replayed through its no-feedback decision path. Rehydration rejects unknown fields and invalid feedback instead of dropping them.

## Replay and reports

`inspect` exposes generic ordered records. `replay-policy` rehydrates each `policy-replay-v1` input through `@arena/core`, runs the policy again, and checks both the recorded decision and post-decision RNG state. A separate `policy-effect-v1` record may correlate a returned skill outcome and the last actual path update to a decision sequence. Pathfinder waypoints may contain fractional block coordinates; the writer and reader preserve finite fractional values, while integer-valued coordinates still follow the trace safe-integer rule above. Those effects are validated and counted; replay does not reproduce client or server actions.

`report` starts from the runner's prepared roster, which for a generalized roster records each seat's controller kind and reserved username and is the run's effective roster record, applies ordered elimination events, checks public states and terminal clocks, and rejects a terminal outcome that contradicts those records. It reports resolved death and disconnect causes from the authoritative elimination stream. It does not infer player actions from policy decisions or raw client events. `compare` performs exact record and range comparison while ignoring only the outer run ID; it does not establish semantic equivalence across runs.

The `replay-report` acceptance source runs a real baseline-policy match with policy recording enabled, requires at least one decision and completed effect, replays its trace three times, and compares the derived report with the live outcome and authoritative events. It also replays byte-identical scratch copies with changed filesystem modification times and checks that the output is unchanged. Trace-v2 and trace-v3 envelopes have no timestamp or log-verbosity fields, and the command has no verbosity mode; the strict schemas reject an added top-level `verbosity` field. These checks make no claim about presentation-layer log output. D1 semantic world equality is checked separately.

D1 semantic world determinism is not implemented by the runner. D2 verifies recorded core policy decisions for the supplied inputs, not the full Mineflayer or Paper trajectory. D3 derives terminal statistics from the supplied control event stream and cannot establish that the stream covers the full run unless its sequence range does. No cross-architecture replay claim is made by these offline checks.

## Civilization replay and result evidence

Civilization decisions use independent closed namespaces: `civilization-policy-input-v1`, `civilization-policy-replay-v1`, and `civilization-policy-effect-v1`. Unmerged experimental civilization records are unsupported. The input retains the validated context and private material/resource/team-message observations, with complete civilization memory and feedback, parameters, and the RNG state. Shared policy memory and feedback are validated through the unchanged Hunger Games v2 rules internally; material failures and bounded action feedback are preserved by the civilization validators. Replay reconstructs the current civilization policy with that feedback, compares the complete decision (including mining, crafting, transfer, placement, and shared survival actions), and verifies the post-decision RNG state. Unknown versions, cross-mode decisions, and effects from the other namespace are rejected.

Civilization action dispositions follow the existing owned-action contract. Checkpoints may contain pending actions; complete traces must join every started civilization action with its settled effect, including cancellation during shutdown. Bounded progress may settle only a validated civilization material action; pending results and progress from shared actions remain invalid. A replaced action remains pending until its own effect settles. The trace builder retains this pending set after the plugin outcome and refuses final publication until all results settle. Resource-aborted partial evidence remains a failure artifact and is never reported as a completed match.

Civilization reports require the terminal authoritative state at the outcome tick, exact scores matching the outcome, living zone occupants, ordered capture-state ticks, and scores that never decrease. Faction elimination winners must agree with reconstructed survivors; tick-limit winners and draws must agree with authoritative scores and the prepared tick limit. This verifies the emitted state and outcome contract; it does not infer absent capture-zone receipts or reproduce Paper physics.

Civilization countdown disconnects keep their original countdown timestamps in the elimination stream. When those eliminations remove a faction or all competitors, the civilization controller resolves the winner or no-survivor draw at match tick zero. Reports accept this first-tick settlement only with matching survivors, exact authoritative civilization state and scores, and the terminal clock; resolution at match tick one or later remains invalid. Hunger Games elimination timestamp checks are unchanged.

## Trace schema 4 and the action funnel

Runs that record policy replay with the baseline policy write trace schema 4. Schema 4 adds one `action-funnel-v1` record per started or cancelled policy action: seat, action sequence (the decision that started it), match tick at start, intent kind, target entity and evaluator-resolved target seat, border knowledge (`current`, `stale`, `unknown`) of the initiating observation, skill outcome kind, and the client's funnel result (`reached` stage, or `stopped` with last stage passed, typed reason, and fixed-point eye-to-body evidence). Target seats and everything else on this record are evaluator metadata; policies never receive them. Readers keep accepting schema 2 and 3; those schemas reject `action-funnel-v1`, and policy replay ignores it.

`report` adds `action_funnel` only when funnel records exist. Per seat it gives decision denominators (proposed, accepted, continued, held, deferred by reason, border knowledge), action counts by intent and skill outcome, and for `approach` and `attack` the number engaged, the number passing each stage, and stops by reason. For attacks with a known target seat it counts those followed by that seat's death elimination within 100 match ticks. The control wire carries no damage event, so the confirmation is an elimination match, not a hit count, and a client claim never counts.

`./arena explain --run-id <id> --seat <n>` lists that seat's decisions with the permitted observation kinds recorded in the input, the resulting actions with skill outcome, funnel stage, confirmed effect, and failures. It reads only recorded evidence.

On failure the runtime writes `diagnostic-rings.json` into the run directory: per seat, the last 128 decisions and action results, with a count of entries dropped by overflow.
