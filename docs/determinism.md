# Determinism and evidence

## TypeScript trace-v2 reading

The TypeScript runner accepts only trace schema version 2. A segment has exactly the required envelope fields and its trailer is exactly `{ "complete": true }`. Generic inspection preserves record objects as written; `report` and `replay-policy` interpret only their documented typed records. Duplicate JSON object names are rejected recursively before a JavaScript object can overwrite one.

A segment's `records` array is the sequential stream. JSON nesting is limited to 32 containers per segment. `first_sequence` and `last_sequence` are canonical unsigned decimal strings from 1 through 18446744073709551615. The number of records must equal `last_sequence - first_sequence + 1`, calculated without integer overflow; array index therefore determines each record's sequence. Across supplied segments, the runner orders by `first_sequence`, requires one `run_id`, and rejects gaps, overlaps, and sequence overflow. This reconstructs a complete ordered span from the supplied files; it cannot establish that the span covers the full run.

The `sha256` field is the lowercase SHA-256 digest of the compact serialization of the `records` array only. The byte sequence is UTF-8 with no whitespace: object keys use JavaScript's default string sort order, arrays keep their order, and numbers use `JSON.stringify` serialization. Non-finite values and integer-valued numbers outside JavaScript's safe integer range are rejected. The digest excludes the envelope, `run_id`, trailer, and checksum text. Producers must use the same canonicalization. Trace-v1 files use numeric sequence fields and a different canonicalization; the TypeScript reader rejects them instead of interpreting them as schema 2.

## Java world-plan transfer

The TypeScript encoder writes world-plan schema version 1 in the field shape consumed by Java `MapPlanReader`: `schema`, `run_id`, `map_semantic_id`, `dimensions`, `blocks`, `spawns`, and `loot_containers`. Blocks and loot containers retain the spec compiler's canonical position order; spawn seats are contiguous from zero and capped at six; loot inventory order is preserved. The compact UTF-8 plan is capped at 128 MiB. Its golden fixture is shared with the Java reader. `prepare` writes the plan to `.work/arena/runs/<run-id>/world-plan.json` using the native handle-relative filesystem helper. It creates the run directory exclusively and publishes the plan without overwriting an existing file.

## Core policy replay input

`@arena/core` normalizes `policy-input-v2` with one validated observation, its policy memory, an ordered feedback batch of at most two completed skill outcomes, parameters, and the pre-decision RNG state. Historical `policy-input-v1` keeps its original memory shape and is replayed through its no-feedback decision path. Rehydration rejects unknown fields and invalid feedback instead of dropping them.

## Replay and reports

`inspect` exposes generic ordered records. `replay-policy` rehydrates each `policy-replay-v1` input through `@arena/core`, runs the policy again, and checks both the recorded decision and post-decision RNG state. A separate `policy-effect-v1` record may correlate a returned skill outcome and the last actual path update to a decision sequence. Pathfinder waypoints may contain fractional block coordinates; the writer and reader preserve finite fractional values, while integer-valued coordinates still follow the trace safe-integer rule above. Those effects are validated and counted; replay does not reproduce client or server actions.

`report` starts from the runner's prepared roster, applies ordered elimination events, checks public states and terminal clocks, and rejects a terminal outcome that contradicts those records. It reports resolved death and disconnect causes from the authoritative elimination stream. It does not infer player actions from policy decisions or raw client events. `compare` performs exact record and range comparison while ignoring only the outer run ID; it does not establish semantic equivalence across runs.

The `replay-report` acceptance source runs a real baseline-policy match with policy recording enabled, requires at least one decision and completed effect, replays its trace three times, and compares the derived report with the live outcome and authoritative events. It also replays byte-identical scratch copies with changed filesystem modification times and checks that the output is unchanged. Trace-v2 has no timestamp or log-verbosity fields, and the command has no verbosity mode; unsupported metadata such as a `verbosity` field is rejected by the strict trace schema. These checks make no claim about presentation-layer log output. D1 semantic world equality is checked separately.

D1 semantic world determinism is not implemented by the runner. D2 verifies recorded core policy decisions for the supplied inputs, not the full Mineflayer or Paper trajectory. D3 derives terminal statistics from the supplied control event stream and cannot establish that the stream covers the full run unless its sequence range does. No cross-architecture replay claim is made by these offline checks.

## Civilization replay and result evidence

Civilization decisions use independent closed namespaces: `civilization-policy-input-v1`, `civilization-policy-replay-v1`, and `civilization-policy-effect-v1`. Unmerged experimental civilization records are unsupported. The input retains the validated context and private material/resource/team-message observations, alongside an unchanged nested `policy-input-v2` survival input containing memory, ordered feedback, parameters, and the RNG state. Replay reconstructs the current civilization policy with that feedback, compares the complete decision (including mining, crafting, transfer, placement, and shared survival actions), and verifies the post-decision RNG state. Unknown versions, cross-mode decisions, and effects from the other namespace are rejected.

Civilization action dispositions follow the existing owned-action contract. Checkpoints may contain pending actions; complete traces must join every started civilization action with its terminal effect, including cancellation during shutdown. A replaced action remains pending until its own effect settles. The trace builder retains this pending set after the plugin outcome and refuses final publication until all results settle. Resource-aborted partial evidence remains a failure artifact and is never reported as a completed match.

Civilization reports require the terminal authoritative state at the outcome tick, exact scores matching the outcome, living zone occupants, ordered capture-state ticks, and scores that never decrease. Faction elimination winners must agree with reconstructed survivors; tick-limit winners and draws must agree with authoritative scores and the prepared tick limit. This verifies the emitted state and outcome contract; it does not infer absent capture-zone receipts or reproduce Paper physics.
